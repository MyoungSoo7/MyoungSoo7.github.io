이번 글의 세 문항은 공개 기출문제의 원문을 재현하지 않은 **창작 문제**다. IETF RFC 8446 원문을 확인해 TLS 1.3의 핵심 개념을 묻도록 구성했다.

## 문제 1 — TLS의 보안 속성

### 문제
RFC 8446이 설명하는 TLS 보안 채널의 주요 목적에 해당하지 않는 것은?

### 선택지
1. 네트워크 도청 방지
2. 전송 중 변조 탐지·방지
3. 메시지 위조 방지
4. 모든 애플리케이션의 권한 부여 정책을 서버 대신 자동 결정

### 정답
4번

### 해설
RFC 8446은 TLS가 도청(eavesdropping), 변조(tampering), 메시지 위조(message forgery)를 막도록 설계된 보안 채널을 제공한다고 설명한다. 애플리케이션의 세부 권한 부여 정책은 TLS가 자동으로 결정하는 범위가 아니라 애플리케이션·인증 인프라의 책임이다.

### 오답 포인트
1~3번은 RFC 8446 초록에 직접 제시된 TLS의 목적이다. 4번은 전송 채널 보안과 애플리케이션 인가를 혼동한 설명이다.

### 출처 또는 검증 근거
IETF, RFC 8446, Abstract: https://datatracker.ietf.org/doc/rfc8446/

## 문제 2 — TLS 1.3 서버 인증

### 문제
TLS 1.3에서 서버 인증에 관한 설명으로 가장 적절한 것은?

### 선택지
1. 암호화만 사용하므로 서버의 신원 인증은 TLS 범위가 아니다.
2. 서버는 인증서와 CertificateVerify 등의 핸드셰이크 메시지를 통해 자신이 교환에 참여한 키를 증명할 수 있다.
3. 서버 인증은 DNS의 TXT 레코드만으로 완료된다.
4. 클라이언트가 보낸 애플리케이션 데이터가 서버 인증서를 대신한다.

### 정답
2번

### 해설
RFC 8446의 핸드셰이크는 인증서(Certificate)와 CertificateVerify 메시지 등을 사용해 서버 인증과 키 교환을 수행한다. 단순히 채널을 암호화하는 것만으로는 상대방이 누구인지 보장되지 않으므로 인증 절차와 인증서 검증이 중요하다.

### 오답 포인트
1번은 TLS의 인증 속성을 부정한다. 3번은 DNS 정보만으로 인증서 기반 TLS 서버 인증이 끝난다고 오해한다. 4번은 애플리케이션 데이터와 핸드셰이크 인증 메시지를 혼동한다.

### 출처 또는 검증 근거
IETF, RFC 8446, §4.4(인증 메시지) 및 §4.4.2~§4.4.3: https://datatracker.ietf.org/doc/rfc8446/

## 문제 3 — 핸드셰이크 무결성과 transcript hash

### 문제
TLS 1.3 핸드셰이크에서 transcript hash의 보안상 의미로 가장 적절한 것은?

### 선택지
1. 핸드셰이크 메시지의 누적 내용을 암호학적으로 요약해 인증·키 도출 과정에서 메시지 변조를 탐지하는 데 사용한다.
2. 서버의 CPU 사용률을 계산해 키 길이를 정한다.
3. 모든 애플리케이션 파일을 압축하는 알고리즘이다.
4. 인증서 만료일을 갱신하는 운영 작업이다.

### 정답
1번

### 해설
TLS 1.3은 핸드셰이크 메시지의 transcript를 암호학적으로 처리해 핸드셰이크의 연속성과 무결성을 인증·키 스케줄과 결합한다. 따라서 중간자가 협상 메시지를 바꾸면 검증 단계에서 불일치가 드러날 수 있다. 이는 파일 압축이나 인증서 갱신 작업과는 다른 기능이다.

### 오답 포인트
2번은 성능 측정과 암호학적 해시를 혼동한다. 3번은 데이터 압축 기능으로 오해한 것이다. 4번은 인증서 운영 절차와 핸드셰이크 무결성 검증을 구분하지 못한 설명이다.

### 출처 또는 검증 근거
IETF, RFC 8446, §4.4.1(The Transcript Hash): https://datatracker.ietf.org/doc/rfc8446/
