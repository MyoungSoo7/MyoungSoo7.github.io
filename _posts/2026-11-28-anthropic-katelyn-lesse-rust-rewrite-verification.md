"앤트로픽 엔지니어는 이제 코드를 거의 읽지 않는다"라는 제목의 요약이 돌고 있습니다. 출처는 Anthropic 플랫폼 엔지니어링 리드 **Katelyn Lesse**가 출연한 The Pragmatic Engineer 팟캐스트입니다. 진행자는 Gergely Orosz이고 2026-11-25 공개, 약 1시간 50분 분량입니다([YouTube](https://www.youtube.com/watch?v=9oNvKMd7xJo), [Apple Podcasts](https://podcasts.apple.com/us/podcast/how-anthropic-builds-software-in-2026-with-katelyn-lesse/id1769051199?i=1000804036461), [뉴스레터 쇼노트](https://newsletter.pragmaticengineer.com/p/how-anthropic-builds-software-in)).

이 글은 그 요약을 그대로 옮기지 않았습니다. **녹취록 전문을 처음부터 끝까지 읽고 요약의 주장을 하나씩 원문과 대조**해서 정리했습니다. 그렇게 읽고 나면 제목이 오해를 부른다는 결론에 이릅니다. 원문의 핵심 문장은 이것입니다.

> "as long as you can really boil something down to like make it verifiable in some way, then you don't have to look at every single line of [Rust] code that's getting written."
> — Katelyn Lesse (Rust 재작성 파트)

코드를 안 읽어도 되는 건 검증 장치를 먼저 깔아둔 경우뿐이라는 뜻입니다. 이 글도 그 순서를 따릅니다.

> **출처 표기 원칙.** 아래 내용은 전부 **앤트로픽 내부자의 1인칭 진술**입니다. 수치(80%, 1/3, 5~6개월 등)는 측정 보고서가 아니라 인터뷰에서 나온 말이고, 본인도 "if I had to put a percentage on it", "I want to say" 같은 단서를 달았습니다. 이 수치들을 중립적인 제3자가 재현하거나 검증한 자료는 **찾지 못했습니다.** 타임스탬프는 공식 쇼노트의 챕터 시각입니다.

## 1. 왜 Rust였나: CPU가 더 이상 무한하지 않았다

챕터 *10:21 The Rust rewrite of the Claude API*

**대상이 된 시스템.** Messages API 계층입니다. Claude가 내보내는 모든 토큰이 이 계층을 지나갑니다. 인증·인가, 토큰화, 과금, 세이프가드 검사를 맡고, 그 아래에 GPU/TPU 추론 계층이 있습니다. 앤트로픽의 자체 앱들도 외부 고객과 **같은 API** 위에서 돕니다.

**출발점.** 약 3년 전 연구 조직에 걸쳐 있던 소수 인원이 만든 **Python 모놀리스**였고, 한때는 단일 GCP 리전에서 돌았습니다. 연구·추론·인프라·제품 팀이 함께 일하기 가장 쉬운 언어라서 Python을 골랐다고 합니다.

**문제가 된 계기.** 요청량이 폭증했습니다. 그중 하나로 슈퍼볼 광고가 언급됩니다. 광고를 보고 API 연동을 짜는 사람은 없지만 모바일 앱은 내려받는데, 그 앱도 결국 같은 API를 통과하기 때문입니다. Lesse는 이렇게 말합니다. "CPU는 원하는 만큼 오토스케일할 수 있는 자원이었는데, 클라우드에 더 달라고 하는 게 예전보다 어려운 대화가 됐다."

**Rust 이전에 해본 것.**
- 리전 추가와 트래픽 라우팅. 이번에는 리전 간 네트워크 대역폭이 걸림돌이 됐습니다.
- 인프라 계층의 작은 효율화.

이것만으로 부족하다는 판단이 서자 엔지니어 한 명이 "Rust를 해보자"고 제안했습니다.

**Go가 아니라 Rust를 고른 이유.** 그 1년 전 새 서비스를 쓸 때는 Go를 택했습니다. 당시엔 "언어 선택이 상관없을 만큼 모델이 좋지 않아서" 사람에게 친숙한 쪽을 골랐다는 설명입니다. 이번에는 모델이 충분히 좋아졌고, 그래서 **팀에 Rust 경험자가 많지 않아도 괜찮다**고 판단했습니다.

### 요약과 원문이 갈리는 곳

| 요약의 주장 | 원문 | 판정 |
| --- | --- | --- |
| CPU 한계 때문에 Python→Rust 재작성 | 위와 같음 | ✅ 일치 |
| Rust 경험 부족, 컴파일러가 안전망 | 컴파일 타임 검사가 많을수록 에이전트 결과를 믿기 쉽다("the more you can get it to be verifiable…") | ✅ 일치 |
| 75:25 협업 | "75%는 모델이 쓰고 문법은 크게 중요치 않다. 25%는 엔지니어가 뭘 하는지 이해하고 싶어 모델에게 질문한다." 본인이 "굳이 퍼센트를 붙이자면"이라고 단서를 닮 | ✅ 일치(체감치) |

> "half the battle is Claude helps you write the code. The other half of the battle is Claude helps you learn what code is being written."

## 2. 검증: 섀도 트래픽과 "프롬프트를 볼 수 없다"는 제약

챕터 *23:40 Verifying the rewrite with shadow traffic*

**계획이 바뀐 과정.** 처음 계획은 시스템을 조각내서 하나씩 Rust로 옮기는 것이었습니다. 진행이 느리던 중 새로 합류한 시니어 엔지니어가 "한 번에 하자(great leap)"고 제안했습니다. 코드베이스를 통째로 포크해 Rust로 다시 쓰는 방식입니다.

**구조.**
1. **아주 얇은 Python 프런트 도어**가 요청을 받습니다.
2. 실제 응답은 기존 Python 시스템이 처리합니다.
3. 같은 요청을 Rust 시스템에 **섀도**로 흘립니다.
4. 날마다 "Python과 Rust의 결과가 다른 요청이 몇 %인가"를 모델에게 집계시키고, 그 비율을 거의 완벽해질 때까지 낮춥니다.

**가장 어려웠던 점은 데이터를 볼 수 없다는 것이었습니다.**

> "we don't look at people's prompts. We don't look at people's completions."

차이가 나도 원본 데이터를 열어 디버깅할 수 없습니다. 그래서 비교 기준을 두 개로 잡았습니다.

- **들어가는 쪽**: 추론 계층으로 내려가기 직전까지의 상태가 같은지
- **나오는 쪽**: 토큰 수가 같은지

**롤아웃.** 롤아웃 중에도 Python 프런트 도어는 **폴백**으로 남겨 두었습니다. Rust 쪽이 오류를 내면 Python으로 처리해서, 조금 느리더라도 응답이 없는 일은 막았습니다. 충분히 안심이 된 다음에야 이 문을 걷어냈습니다.

### "PR 80%를 안 읽었다"의 정확한 맥락

요약에서 가장 자극적인 수치입니다. 원문은 이렇습니다.

> "If you were to ask the team, they would probably say something like 80% of the pull requests that got opened by agents, they didn't deeply read through all of the code… and then I would say like 20% probably is where … they kind of had to dig deep into the details."

주의할 점이 세 가지 있습니다.

1. **범위**: 회사 전체 통계가 아니라 **이 Rust 재작성 프로젝트** 이야기입니다.
2. **성격**: "팀에 물어보면 아마 이렇게 말할 것"이라는 **체감치**입니다.
3. **같은 단락의 앞 문장**: "시스템이 워낙 중요해서, 생각보다 엔지니어들이 코드 세부에 더 많이 들어갔다"는 말이 바로 앞에 붙어 있습니다. 즉 이 시스템에서는 평소보다 **더 많이** 읽었다는 뜻입니다.

80%를 안 읽어도 된 건 섀도 비교라는 오라클이 있었기 때문입니다. 오라클 없이 80%를 건너뛰는 것과는 다른 이야기입니다.

### 기간과 병목

**기간.** Lesse는 "something on the order of like maybe five or six months"라고 했습니다. 사전 조사 기간을 포함한 말이고, 쇼노트 인트로에는 "5개월"로 나옵니다. 작은 핵심 팀이 맡았습니다.

**진짜 병목은 다른 팀과의 조율이었습니다.**
- 재작성이 진행되는 동안에도 다른 팀들은 Python 시스템을 계속 개발했습니다.
- 한 번은 어떤 베타 기능이 Python 쪽에서 예고 없이 GA로 전환됐고, 섀도 비교에 차이가 쏟아졌습니다.
- 그 뒤로 **린트와 정적 분석으로 "Python과 Rust 양쪽을 다 구현하라"를 강제**했습니다.

요약의 "대부분의 시간이 조율에 쓰였다"는 원문과 맞습니다. 다만 이 말은 진행자가 먼저 정리했고 Lesse가 동의한 것입니다.

## 3. Claude Managed Agents: 출시 전에 통째로 다시 지었다

챕터 *44:35 Building Claude Managed Agents*

Managed Agents는 에이전트를 정의하고 세션을 실행하는 상위 API입니다. Claude Code의 웹·모바일 경험도 같은 아키텍처 위에서 돕니다. 첫 구현은 단순했습니다. 요청이 오면 샌드박스를 띄우고 그 안에서 Claude Code를 부팅하는 방식입니다. 이 방식에서 문제가 네 가지 나왔습니다.

| 문제 | 첫 설계 | 재설계 |
| --- | --- | --- |
| 신뢰성 | 샌드박스가 죽으면 에이전트도 죽음 | 하네스를 **내구성 있는 서버**에서 실행하고, 샌드박스는 작업 실행용으로 필요할 때만 띄움 |
| 지연 | 샌드박스 부팅 → Claude Code 부팅을 거친 뒤에야 첫 토큰 | 요청이 내구 서버에서 곧장 Messages API로 감 |
| 보안 | 자격증명이 에이전트와 같은 샌드박스 안에 있음 | 옆에 프록시를 두고 자격증명은 볼트에 보관, **egress 시점에 주입**해서 샌드박스에 들어가지 않음 |
| CPU | 세션마다 샌드박스 1개 이상 | 원래 시스템 대비 **평균 약 1/3** ("around a third of the CPU") |

얼리 베타까지 낸 뒤에 이 결정을 내렸습니다. Lesse는 "작은 결정이 아니었다"고 강조합니다. 그래도 구현 비용이 크게 줄어든 상황이라 다시 짓는 쪽이 값어치가 있다고 봤다는 설명입니다.

**정정.** 일부 애그리게이터 기사에는 "Messages API CPU 최대 50% 절감"이라는 수치가 돌지만 **녹취록에서는 찾을 수 없었습니다.** 원문에 있는 CPU 수치는 위의 Managed Agents "약 1/3"뿐입니다. Rust 재작성의 효과에 대해서는 "CPU를 이만큼 아꼈고 지연이 이만큼 좋아졌다"는 식의 정성적 언급만 있고 숫자는 나오지 않습니다.

## 4. 리뷰는 '없어진' 게 아니라 '분류'된다

챕터 *1:04:47 Human code review*

> "we have a system that, I mean, it's a Claude, but it's a classifier … it runs on every change and it decides, does this need a human look? If so, how many humans and what teams does it need? Or is this something that can merge directly without a human looking at it?"

이 분류기가 하는 일과 현재 수준은 이렇습니다.

- **무인 머지 대상.** SDK 버전 범프처럼 "백만 번 해본, 다 똑같이 생긴" **기계적 변경**입니다. 이때 Claude는 변경이 원래 의도한 결과를 내는지 확인합니다.
- **사람을 부르는 경우.** 위험한 변경, 부작용이 의심되는 변경, 아직 무인 머지를 신뢰하지 않는 시스템의 변경입니다.
- **현재 규모.** "지금은 무인 머지가 **소수**이고 래칫으로 늘리는 중이다." 위험한 변경은 여전히 사람이 봅니다.

**사람 없이 도는 루프도 있습니다.**
- CI가 빨개지면(예: flaky 테스트가 main에 들어옴) 에이전트가 고칩니다.
- 사람이 적어둔 "이 시스템은 이렇게 동작해야 한다"는 명세를 들고 QA 에이전트가 계속 두드려 보고, 고장이 나면 PR을 올립니다.

## 5. 온콜과 온보딩

챕터 *1:06:41 Oncall with Claude*, *31:11 Onboarding new hires with Claude*

### 온콜

부하가 큰 API 온콜 로테이션에 지난 몇 달 동안 **Claude가 섀도로** 붙어 있었습니다. 지금은 페이지가 오면 Claude에게 먼저 가는 방식을 "막 시작하는 단계"입니다.

- **1차 관문은 "소음인가, 진짜인가"입니다.** 소음이면 사람을 깨우지 않습니다.
- 진짜라서 사람을 호출하면, 사람이 노트북 앞에 앉을 즈음 Claude가 진단과 수정안을 갖춰 두는 경우가 많다고 합니다.
- 다만 "**아직 거기까지는 아니다.** 지금은 주로 소음 판별"이라고 선을 긋습니다.

### 온보딩

신규 입사자는 Claude에게 "이게 어떻게 돌아가는지 알려줘"라고 묻습니다. 그러면 클릭해 가며 볼 수 있는 인터랙티브 시스템 맵이나 글, 팟캐스트 형식의 설명이 나옵니다. 사내 시스템마다 **MCP 서버**가 연결돼 있지만, 대부분은 "그냥 코드베이스 자체"를 읽는다고 합니다.

### 요약 정정

요약에는 "MCP로 온콜 알림 1차 필터링"이라고 나오는데, 원문에서 MCP가 언급되는 곳은 **사내 시스템 연결과 온보딩 맥락**입니다. 온콜 섀도가 MCP로 구현됐다는 말은 원문에 없습니다.

## 6. PM이 프로덕션에 배포했다. 그래도 책임은 소유 팀에 있다

챕터 *1:09:31 Product managers shipping to production*

개발자 콘솔의 **프롬프트 캐시 진단 대시보드**는 PM이 Slack에서 Claude와 주고받으며 구현해 프로덕션까지 냈습니다. 캐시 미스가 나면 API 응답이 그 이유를 알려주는 기능입니다. 단서가 두 가지 붙습니다.

- 그 PM은 "비교적 기술적인 사람"이었고, 엔지니어들이 코드를 리뷰했습니다.
- 코어 API 변경을 PM이 직접 하는 단계는 아닙니다.

**책임의 원칙은 그대로입니다.** 문제가 생기면 페이지를 받는 건 그 시스템을 소유한 **개발자 경험(DevEx) 팀**입니다. 사람이 끼지 않는 에이전트 변경(SDK 범프, CI 자동 수정)에도 같은 원칙을 적용합니다. 그래서 팀은 지금도 **투 피자 팀(5~10명)** 크기를 유지합니다. 시스템을 이해하고 책임질 인간 단위가 필요하다는 이유입니다. 구성은 예전보다 시니어 쪽으로 기울었습니다.

## 7. 코딩 면접은 '폐지'가 아니라 '단계적 축소'

챕터 *1:24:13 Phasing out traditional coding interviews*

Lesse는 "I'm being pretty specific with the phrase **phased out**"이라고 일부러 표현을 골랐습니다.

- **바뀐 이유.** 코딩 면접은 떨어지는데 나머지 면접은 압도적으로 잘 보는 후보가 늘었습니다. 평소에 손으로 코드를 쓰지 않기 때문입니다.
- **대체 실험.**
  - 에이전트가 쓴 코드 리뷰하기
  - 에이전트가 만든 시스템 설계 리뷰하기
  - 코딩 에이전트로 무언가 만들기
  - 정답은 아직 정하지 않았습니다. 신호의 신뢰도, 채점 부담, 루브릭의 편향을 함께 따져보는 중입니다.
- **그대로인 것.** 기술 설계 면접과 과거 프로젝트 면접입니다.

진행자 Orosz는 아웃트로에서 "알고리즘 코딩 면접을 완전히 없앴다"고 더 강하게 정리합니다. 이건 **진행자의 해석**입니다. 본인의 표현은 "phased out"입니다.

## 8. 정체성 위기: 조언의 실체는 '토대'

챕터 *1:33:21 The software engineer identity crisis*

Lesse의 주장은 이렇게 요약됩니다. 에이전트 수천 개가 신약 허가 패키지나 법률 실사 전 과정처럼 큰 문제를 맡는 시대로 가려면 먼저 풀어야 할 공학 문제가 있습니다.

- **보안, 인증·신원, 인프라**
- 외부 시스템 연동 표준. Lesse 팀원 몇 명이 MCP를 만들었고 지금도 코어 메인테이너입니다.

이걸 제대로 깔지 않고 에이전트를 풀어놓으면 "좋은 문제를 풀기 전에 나쁜 문제가 먼저 터진다"는 것입니다. 그래서 그녀의 조언은 둘입니다.

1. **야망 수준을 올려라.**
2. 지금 당장의 문제 하나를 풀려고가 아니라, **앞으로 복잡해질 문제를 내다보고** 보안 같은 영역에서 깊은 전문성을 쌓아라.

엔지니어의 일은 결국 **조율**로 수렴한다고도 말합니다. 아이디어가 현실이 되기까지 사람과 팀과 에이전트가 같은 그림을 보게 만드는 일입니다.

## 우리 쪽 답: "에이전트 코드를 안심하고 넘기려면 무엇부터 갖추나"

요약글은 이 질문으로 끝납니다. 인터뷰에서 얻을 교훈은 리뷰를 빼는 기술이 아니라 **사람의 리뷰를 대신할 오라클을 먼저 세우는 순서**라고 봅니다. 저는 아래 순서로 갖추겠습니다. 마지막 항목은 실제로 당해본 일입니다.

1. **차이를 재는 오라클.** 재작성이나 마이그레이션이라면 섀도 비교가 정답 장치입니다. 비교 기준(들어가는 상태, 나가는 결과의 요약값)은 코드보다 먼저 정해야 합니다.
2. **기계가 강제하는 경계.** 컴파일러, 타입 검사, 아키텍처 테스트(ArchUnit 등)가 여기 해당합니다. Lesse가 Rust를 반긴 이유도 결국 "컴파일되면 버그 한 종류가 사라진다"는 데 있습니다.
3. **위험도 분류.** 기계적 변경과 위험한 변경을 나눠 사람의 주의를 위험한 쪽에만 씁니다. 처음에는 무인 머지 범위를 아주 좁게 잡고 래칫으로 넓힙니다.
4. **소유 팀과 폴백.** 문제가 났을 때 누가 페이지를 받는지, 어디로 되돌릴지(Python 프런트 도어 같은 것)를 미리 정해 둡니다.
5. **게이트가 공허하게 통과하지 않는지 확인.** 저희 쪽 아키텍처 테스트가 **검사 대상 클래스를 0개 임포트한 채 초록불**을 낸 적이 있습니다. "검사할 것이 없으면 실패"하는 가드가 없으면 오라클 자체가 거짓말을 합니다. 검증 장치도 검증해야 합니다.
