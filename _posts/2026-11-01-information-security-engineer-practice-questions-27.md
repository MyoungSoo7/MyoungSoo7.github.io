이번 글의 세 문항은 공개 기출문제의 원문을 재현하지 않은 **창작 문제**다. 정답과 해설은 게시 시점에 확인한 IETF RFC 8446 및 NIST 공개 문서를 근거로 작성했다.

## 문제 1 — TLS의 보안 목적

### 문제
RFC 8446이 설명하는 TLS의 주된 목적에 가장 가까운 것은?

### 선택지
1. 신뢰할 수 없는 전송망 위에서 통신 당사자 사이의 보안 채널을 제공한다.
2. 모든 애플리케이션의 사용자 권한을 중앙에서 결정한다.
3. 데이터베이스의 백업 주기를 자동으로 설정한다.
4. 네트워크 라우팅 경로를 암호화 없이 최적화한다.

### 정답
**1번**

### 해설
RFC 8446은 TLS가 도청, 변조, 메시지 위조를 막도록 설계된 통신을 지원하며, 통신하는 두 피어 사이에 보안 채널을 제공한다고 설명한다. TLS는 애플리케이션 통신 보호 프로토콜이지 사용자 권한관리나 백업정책 자체를 대신하는 시스템은 아니다. [1]

### 오답 포인트
TLS를 인증·인가·백업까지 모두 해결하는 통합 보안 기능으로 이해하면 안 된다. TLS가 제공하는 보호 범위와 애플리케이션의 접근통제 범위를 구분해야 한다.

### 출처 또는 검증 근거
[1] IETF, *RFC 8446 — The Transport Layer Security (TLS) Protocol Version 1.3*, Abstract 및 §1, https://datatracker.ietf.org/doc/html/rfc8446

## 문제 2 — TLS 1.3의 0-RTT

### 문제
TLS 1.3의 0-RTT 데이터를 사용할 때 특히 주의해야 할 보안 특성은 무엇인가?

### 선택지
1. 재전송 공격 가능성을 고려해야 하므로 모든 요청에 무조건 사용해야 한다.
2. 초기 데이터의 재전송 위험을 고려하고, 재실행되어도 안전한 요청에 제한하는 것이 적절하다.
3. 0-RTT는 서버 인증서 검증을 영구적으로 제거한다.
4. 0-RTT는 암호화가 전혀 적용되지 않는 평문 전송이다.

### 정답
**2번**

### 해설
RFC 8446은 0-RTT 및 재전송 방지를 별도 절로 다루며, 초기 데이터가 재전송될 수 있는 특성을 고려하도록 한다. 따라서 결제·상태 변경처럼 재실행이 치명적인 요청에는 별도의 재전송 방지 설계나 0-RTT 제한이 필요하다. [1]

### 오답 포인트
0-RTT를 단순히 “더 빠른 TLS”로만 외우면 재전송 위험을 놓친다. 또한 0-RTT가 평문이라는 설명도 틀리며, 핵심은 보호 수준과 재전송 성질을 함께 평가하는 것이다.

### 출처 또는 검증 근거
[1] IETF, *RFC 8446*, §2.3, §8, https://datatracker.ietf.org/doc/html/rfc8446

## 문제 3 — 트래픽 키 갱신

### 문제
TLS 1.3에서 트래픽 비밀값을 갱신하는 기능을 운영 보안 관점에서 해석한 것으로 옳은 것은?

### 선택지
1. 연결이 성립하면 세션 동안 키를 절대 바꿀 수 없다.
2. 키 갱신은 트래픽 키를 교체하는 절차이며, 키 사용 한도와 함께 관리해야 한다.
3. 키 갱신은 서버 운영체제의 관리자 계정 비밀번호 변경을 뜻한다.
4. 키 갱신은 인증서 발급기관을 교체하는 절차와 동일하다.

### 정답
**2번**

### 해설
RFC 8446은 트래픽 비밀값 갱신과 키 계산, 키 사용 한도를 별도로 규정한다. 따라서 TLS 연결의 암호 키 수명과 사용량을 프로토콜 절차에 맞춰 관리하는 것이 맞으며, 이는 운영체제 계정이나 인증서 발급기관 교체와 동일한 개념이 아니다. [1]

### 오답 포인트
“TLS 키”라는 표현을 인증서·개인키·세션 트래픽 키와 구분하지 않으면 오답이 된다. 문제에서 말하는 트래픽 키 갱신과 PKI 인증서 갱신은 서로 다른 생명주기다.

### 출처 또는 검증 근거
[1] IETF, *RFC 8446*, §4.6.3, §5.5, §7.2, https://datatracker.ietf.org/doc/html/rfc8446
