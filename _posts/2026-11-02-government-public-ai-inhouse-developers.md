> 기준 시각: 2026-11-02 15:51 KST. 헬로디디 기사를 바탕으로 내용을 재구성하고, 정부 내부 개발 역량·공공 AI 운영 관점에서 분석했다. 기사에 없는 예산·서비스 목록·기술 스택·성과지표는 사실처럼 추가하지 않았다.

## 결론

정부가 국민용 AI 서비스를 외부 업체에 전적으로 맡기는 방식에서 벗어나 **민간 개발자와 공공 인력을 결합한 내부 개발 조직을 운영하려는 시도**가 시작됐다.[1] 핵심은 개발자 26명의 숫자 자체보다, 국민의 불편을 발견하고 서비스를 설계·개발·운영하는 역량을 정부 안에 축적할 수 있는지다.

## 1. 기사에서 확인되는 조직 구성

헬로디디는 과학기술정보통신부가 국민AI서비스혁신추진단을 본격 가동하고, 김세웅 전 카카오 부사장을 추진단장으로 선임했다고 보도했다.[1]

기사에 따르면 추진단은 다음과 같은 구조다.

| 구분 | 인원·역할 |
| --- | --- |
| 전체 조직 | 61명 |
| 민간 채용 개발자 | 26명, 전체의 약 43% |
| 공공 AI 인력 | AI 개발 역량을 갖춘 AI챔피언 16명 |
| 부처 인력 | 13명 |
| 유관기관 전문가 | 6명 |
| 조직 체계 | 1단 1관 4팀: 기획총괄, 개발 1·2, 개발인프라보안 등 |

추진단은 기존 외주 중심 정부 정보화 사업과 달리 내부 개발자가 국민의 불편과 수요를 직접 찾아 서비스를 설계·개발하는 방식을 지향한다고 소개됐다.[1]

과기정통부는 11월 초부터 민간 개발자를 추가 채용할 계획이며, 채용 분야·인원·자격요건은 과기정통부와 나라일터 공고로 안내한다고 밝혔다.[1]

## 2. 왜 공공 AI에 내부 개발 역량이 필요한가

공공서비스는 단순히 모델 API를 연결한다고 완성되지 않는다.

```text
국민의 불편
  → 정책·법령·업무 규칙
  → 데이터·자격·권한
  → AI 기능
  → 담당 공무원 업무 흐름
  → 민원·감사·장애 대응
```

외부 업체가 개발을 잘못한다는 의미가 아니라, 정부가 문제 정의·우선순위·데이터 권한·운영 책임을 내부에서 이해하지 못하면 다음 문제가 생길 수 있다.

- 요구사항이 계약 문서 중심으로 고정됨
- 실제 국민 사용성보다 납품 산출물에 집중
- 운영 중 정책 변경에 느리게 대응
- 장애·보안·개인정보 이슈에서 책임 경계가 불명확
- 특정 업체와 시스템 지식이 강하게 결합
- 다음 사업에서 같은 설계와 시행착오를 반복

내부 개발 조직은 이런 문제를 줄일 수 있는 기반이다. 다만 내부화가 곧 성공을 의미하지는 않는다. 공공 조직에도 제품 관리, 보안, 개인정보, 조달, 운영, 사용자 연구 역량이 함께 있어야 한다.

## 3. 민간 개발자와 공공 인력의 결합 모델

이번 추진단의 설계에서 중요한 점은 민간 개발자만 투입하는 것이 아니라 AI챔피언·부처 인력·유관기관 전문가를 함께 배치한다는 점이다.[1]

```text
민간 개발자
  └─ 개발 속도·서비스 구현·현대적 엔지니어링

공공 AI 인력
  └─ 공공 업무 이해·내부 확산·현장 연결

부처 인력
  └─ 정책·법령·행정 절차·책임 구조

유관기관 전문가
  └─ 도메인·기관 시스템·현장 제약
```

이 조합은 한쪽만으로는 해결하기 어려운 문제를 다룬다.

- 민간만 있으면 정책·책임·기관 간 조정이 약해질 수 있음
- 공공만 있으면 제품 개발 속도와 최신 실행 방식이 부족할 수 있음
- 기술 전문가만 있으면 실제 국민 여정과 행정 책임을 놓칠 수 있음

성공 조건은 직군을 섞는 것 자체가 아니라, 공동 backlog·명확한 의사결정권·코드 소유권·운영 책임을 설계하는 것이다.

## 4. 외주에서 내부 개발로 바꿀 때 생기는 과제

### 4.1 조직의 속도와 공공 책임의 충돌

민간 서비스는 빠른 실험과 반복을 중시하지만, 공공서비스는 개인정보·접근성·보안·법적 근거·감사 추적성을 요구한다. 따라서 “민간처럼 빠르게”를 무조건적인 절차 생략으로 해석하면 안 된다.

권장 흐름은 다음과 같다.

```text
작은 범위의 시범 서비스
  → 개인정보·보안·접근성 검토
  → 실제 사용자 실증
  → 로그·오류·만족도 분석
  → 제한적 확대
  → 운영 표준화
```

### 4.2 인력 유지와 지식 이전

민간 개발자를 단기 계약 인력처럼만 활용하면 추진단 종료 후 다시 지식 공백이 생길 수 있다. 다음을 계약·운영 초기에 명확히 해야 한다.

- 소스코드와 배포 설정의 기관 소유·관리
- 설계 문서·ADR·운영 runbook
- 테스트와 장애 대응 절차
- 코드 리뷰와 공동 커밋 체계
- 공공 인력 대상 지식 이전
- 계약 종료 후 유지보수·취약점 대응 주체

“내부 개발”은 사무실 안에서 직접 코딩한다는 뜻만이 아니라 **기관이 시스템을 이해하고 계속 바꿀 수 있는 상태**를 의미해야 한다.

### 4.3 AI 서비스의 운영 책임

AI 서비스는 일반 웹서비스보다 답변 품질과 실패 양상이 복잡하다.

- 잘못된 답변과 근거 없는 확신
- 최신 법령·정책 반영 지연
- 개인정보·민감정보 노출
- 프롬프트 인젝션과 데이터 오염
- 모델·검색 인덱스 변경에 따른 품질 변동
- 장애 시 대체 경로와 사람 상담 연결

따라서 서비스마다 다음을 정해야 한다.

```text
허용 업무
금지 업무
출처 표시 방식
사람에게 넘기는 조건
로그·보존 기간
모델 변경 승인자
품질·보안·개인정보 지표
```

## 5. 국민용 AI 서비스의 검증 설계

국민용 서비스의 성공을 “AI를 붙였다”로 판정하면 안 된다. 최소한 다음 지표를 분리해야 한다.

| 영역 | 검증 질문 |
| --- | --- |
| 이용성 | 국민이 실제로 문제를 해결했는가? |
| 정확성 | 답변이 공식 자료와 일치하는가? |
| 근거성 | 출처와 기준시각을 제시하는가? |
| 안전성 | 개인정보·권한·유해 요청을 통제하는가? |
| 접근성 | 장애·고령·저사양 환경에서도 이용 가능한가? |
| 운영성 | 장애·모델 오류·트래픽 증가에 대응하는가? |
| 공정성 | 특정 지역·집단에 불리한 결과가 반복되지 않는가? |
| 책임성 | 누가 승인·수정·중단할 수 있는가? |

권장 판정은 다음처럼 증거를 분리하는 것이다.

```text
PASS        정확성·보안·운영 기준을 모두 충족
WARN        일부 지표 부족, 제한된 범위에서 운영
FAIL        중대한 오류·보안·개인정보 위험
UNVERIFIED  실제 사용자·운영·독립 평가 증거 부족
```

기사에는 추진단이 만들 구체적인 AI 서비스 목록이나 성과 수치가 제시되지 않았다. 따라서 현재는 **조직 출범과 인력 구성은 확인되지만, 국민 체감 성과는 아직 검증 전**이라고 보는 것이 정확하다.[1]

## 6. 기술 아키텍처의 권장 경계

국민용 AI를 설계할 때 모델을 서비스의 중심이 아니라 검증 가능한 한 계층으로 배치해야 한다.

```text
국민 채널
  ↓
인증·동의·접근성·rate limit
  ↓
업무 API·정책 엔진·권한 검사
  ↓
검색/RAG·공식 데이터·출처 관리
  ↓
모델 추론
  ↓
출력 검증·개인정보 필터·사람 escalation
  ↓
감사 로그·품질 지표·장애 대응
```

핵심 원칙은 다음과 같다.

- 모델이 직접 데이터베이스를 무제한 조회하지 않도록 업무 API로 제한
- 답변에 사용한 공식 문서·버전·기준시각 기록
- 개인정보와 행정 식별자를 최소 수집·최소 보존
- 고위험 행정 판단은 자동 확정하지 않고 담당자 검토
- 모델·프롬프트·검색 인덱스 변경을 버전 관리
- 테스트셋과 실제 운영 샘플을 분리
- 장애 시 일반 민원·상담 경로로 안전하게 전환

## 7. 정부 내부 개발 조직의 성공 조건

이번 조직이 지속 가능한 역량으로 자리 잡으려면 다음 다섯 가지가 필요하다.

### 1) 문제 선택

AI를 적용할 수 있는 업무가 아니라, 국민 불편이 크고 개선 효과를 측정할 수 있는 업무부터 선택해야 한다.

### 2) 작은 제품 단위

대규모 통합 플랫폼을 먼저 만들기보다, 좁은 사용자 여정 하나를 끝까지 해결하는 서비스부터 시작해야 한다.

### 3) 운영 권한

개발팀이 코드만 쓰고 배포·로그·장애 대응 권한이 없으면 내부 개발의 장점이 사라진다. 단, 권한은 승인·감사·최소권한 원칙과 함께 설계해야 한다.

### 4) 공공형 엔지니어링 표준

테스트·보안 스캔·개인정보 영향 검토·접근성·감사 로그·rollback을 개발 완료 조건에 포함해야 한다.

### 5) 성과 공개

서비스 수나 생성 코드량보다 실제 이용 완료율, 오류율, 처리시간, 민원 감소, 재방문, 취약점, 운영비를 공개해야 한다.

## 확인된 사실·해석·미확인

- **확인된 사실:** 헬로디디는 국민AI서비스혁신추진단의 출범, 김세웅 단장 선임, 61명 조직, 민간 개발자 26명, 1단 1관 4팀 구성을 보도했다.[1]
- **확인된 사실:** 추진단은 외주 중심 방식에서 벗어나 내부 개발자가 국민 불편과 수요를 찾아 AI 서비스를 설계·개발하는 방향으로 소개됐다.[1]
- **확인된 사실:** 과기정통부는 11월 초 민간 개발자 추가 채용 계획을 밝혔다.[1]
- **해석:** 이번 조직은 공공 AI의 외주 의존도를 낮추고 문제 정의·개발·운영 역량을 내부에 축적하려는 시도로 볼 수 있다.
- **미확인:** 구체적인 서비스 목록, 예산, 모델·클라우드 구성, 일정, 실제 사용자 성과, 보안·개인정보 평가 결과는 기사에서 확인되지 않았다.
